# Version 0.7.1 Review-Card and Standard-Part Discovery Design

**Date:** 2026-09-01

**Target release:** `0.7.1`

**Source baseline:** the current `codex/normal-design-confirmation-v0.7.0`
branch, including the previously reviewed normal-design confirmation and
selected Design Lesson publication work.

## 1. Goal

Version 0.7.1 fixes the Design Lesson review-card lifecycle so a corrected
candidate set can be evaluated after `candidate_errors`, without overwriting a
frozen card from another model revision. It also strengthens the project-owned
`freecad-standard-parts` skill so a structured-provider miss cannot be
misreported as evidence that a commercially available component does not
exist.

The release must preserve existing confirmation, validation, publication,
standard-part provenance, packaging, and public-repository contracts.

## 2. Confirmed Behavior

### 2.1 Candidate validation and freezing

- Candidate validation runs entirely before formal review-card publication.
- When candidate validation fails, the session records `candidate_errors` and
  the validation diagnostics. It does not create a formal review-card file and
  does not bind a review path or review SHA-256.
- A corrected candidate set for the same design and model SHA-256 may be
  submitted again. If validation succeeds, it creates the formal card and
  changes the state to `review_pending`.
- A successfully created card is immutable. Submitting different valid content
  for the same design and model SHA-256 must not replace it.

### 2.2 Model-revision identity

Formal review-card filenames include the full model SHA-256:

```text
lesson-review/review-<64-character-model-sha256>.json
```

This makes model revision part of the storage identity. A new model revision
can create a new card without modifying or deleting an earlier revision's
card. The review-card body, recorded state, validation evidence, and model
confirmation must all refer to the same model SHA-256.

### 2.3 Legacy review-card compatibility

Existing workspaces may contain the legacy path
`lesson-review/review.json`. The workflow must retain that file unchanged.

- If the active session already binds the legacy file as a valid pending,
  retry-required, declined, or published review, existing decision and retry
  behavior remains valid.
- A new model revision never attempts to overwrite the legacy file. It writes
  the new hash-addressed path.
- No automatic migration, rename, deletion, or content rewrite of legacy
  immutable evidence is performed in this release.

### 2.4 Atomicity and failure behavior

Hash-addressed cards continue to use exclusive-create atomic publication and
read-only permissions. Session state changes to `review_pending` only after
the card exists and its SHA-256 matches the canonical bytes. A write or
integrity failure leaves the session without a newly bound review card and
does not mutate older evidence.

## 3. Standard-Part Discovery Policy

The project-owned `.agents/skills/freecad-standard-parts` skill remains the
source for distributable standard-part behavior. Its entry point and provider
reference must state the following rules.

### 3.1 Structured providers are the first pass, not the entire search space

The Agent first uses configured structured providers in their governed trust
order: installed FreeCAD workbenches, STEP.parts, and the verified local
FCStd/STEP catalog. A zero-result response from those sources means only that
the configured structured search did not match.

It must not be treated as evidence that no commercial or standard component
exists.

### 3.2 Semantic decision to expand discovery

After a structured miss, the Agent evaluates the component's mechanical
function, interfaces, operating principle, dimensional envelope, motion,
load-related attributes, and industry vocabulary. When that evidence makes a
commercial off-the-shelf component reasonably likely, the Agent must expand
the search without waiting for a predefined component-type mapping.

The Agent derives source selection and query vocabulary from component
semantics. Examples include functional synonyms, interface standards,
manufacturer terminology, dimensional series, actuation method, mounting
style, and industry-specific names. Examples illustrate query construction;
they do not create an exhaustive routing taxonomy.

### 3.3 Authoritative public sources

Extended discovery prefers, as applicable:

1. manufacturer product catalogs, official product pages, datasheets,
   selectors, configurators, and CAD portals;
2. standards-body or industry-association records that establish the component
   identity or interface standard;
3. authorized distributor catalogs that preserve the manufacturer, exact
   order code, and primary-document links.

General marketplaces, forums, reposted files, and unattributed CAD mirrors are
not authoritative evidence. They may supply search vocabulary but cannot by
themselves establish provenance or authorize CAD reuse.

### 3.4 Result and miss handling

- Preserve manufacturer, order code, standard, nominal size, source URL,
  source revision or access identity, license or reuse terms, and SHA-256 for
  downloaded files.
- Present ambiguous candidates rather than silently choosing among materially
  different interfaces.
- Record the structured providers, extended authoritative sources, query terms,
  and material result of each search stage.
- Network or DNS failure remains inconclusive.
- Only after a reasonable semantic expansion across applicable authoritative
  sources may the Agent report that no suitable component was found.
- A miss never authorizes custom substitute geometry. That exception still
  requires explicit user approval.

## 4. Implementation Boundaries

The lifecycle change is limited to the review-card preparation path and its
tests. It does not change approval-language classification, validation gates,
publication selection semantics, knowledge database schemas, or the meaning of
existing review statuses.

The skill change updates the project-owned skill and its provider reference.
It does not add a web-search dependency, hard-code a universal manufacturer
list, update pinned vendor sources, or change the standard-part cache format.

Generated design artifacts, runtime databases, and customer-specific evidence
remain outside the public repository.

## 5. Test Design

Focused lifecycle tests must prove:

1. invalid candidates produce `candidate_errors`, no review path/SHA binding,
   and no new review-card file;
2. corrected candidates for the same design and model SHA-256 create one
   hash-addressed immutable card and transition to `review_pending`;
3. different valid content for that frozen design and model SHA-256 is rejected;
4. a legacy immutable `review.json` from model revision A remains byte-for-byte
   unchanged while revision B creates its own hash-addressed card;
5. publication approval and selected-lesson publication still consume the
   exact bound card;
6. Windows and POSIX paths use `pathlib` and the same relative-path contract.

Skill validation must run the repository skill validator and confirm that the
entry point routes readers to the provider reference. Review must verify the
new instructions are semantic rather than an exhaustive component-type list,
preserve provenance rules, and distinguish structured misses, authority-search
misses, and network failures.

The release gate includes focused tests, the complete supported offline suite,
public repository and distribution tests, skill validation, wheel and sdist
builds, clean installation and entry-point checks, and the required GitHub
Windows workflow.

## 6. Version and Release

All project-owned version declarations and exact-version tests change from
`0.7.0` to `0.7.1`. `CHANGELOG.md` receives a dated 0.7.1 entry covering the
review-card lifecycle fix and semantic authoritative-source expansion.

After local verification, the implementation branch is merged into local
`main` without discarding the earlier 0.7.0 upgrade commits. `main` is pushed
to GitHub. The required GitHub checks must pass for the pushed commit before
creating and pushing annotated tag `v0.7.1` and publishing the GitHub Release.
Release notes summarize both the previously unreleased 0.7.0 work and the
0.7.1 corrections. No package registry publication is implied.

## 7. Acceptance Criteria

- Candidate errors never create or freeze a formal review card.
- Corrected candidates can progress to `review_pending` for the same model.
- Immutable cards from earlier model revisions remain unchanged and do not
  block new revision cards.
- Current publication and selected-publication tests remain passing.
- The distributable standard-part skill requires semantic authoritative-source
  expansion after applicable structured misses.
- A structured zero result alone can never support a final “not found” report.
- All 0.7.1 version, build, installation, release-boundary, and supported
  offline tests pass.
- GitHub `main`, tag `v0.7.1`, and the GitHub Release refer to the same verified
  commit.
